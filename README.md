# Сервис обработки платежей

Это тестовое задание для компании Secunda. В реализации я старался не усложнять
предметную часть, а сосредоточиться на местах, где асинхронный сервис обычно начинает
ломаться: конкурентных запросах, разрыве между PostgreSQL и RabbitMQ, повторной доставке
и восстановлении после падения процесса.

## Основные решения

Платёж и событие для его обработки создаются в одной транзакции PostgreSQL. API не
публикует сообщение в RabbitMQ напрямую: эту работу выполняет отдельный publisher,
читающий transactional outbox. Поэтому принятый запрос не теряется, если брокер в этот
момент недоступен. Подтверждение RabbitMQ записывается в outbox отдельно, а неизбежное
окно между confirm и `published_at` учитывается как at-least-once доставка.

Идемпотентность создания опирается на уникальное ограничение в БД. Предварительная
проверка ключа используется только для быстрого ответа, а конкурентную гонку окончательно
разрешает PostgreSQL. Повтор с тем же ключом и тем же содержимым возвращает созданный
платёж, повтор с изменёнными данными считается конфликтом.

Publisher и consumer разделены на самостоятельные процессы и независимо масштабируются.
В локальном Compose запущено по два экземпляра каждого, поэтому работа с несколькими
воркерами проверяется не только на уровне интерфейсов. Захват outbox и платежей сделан
через ограниченные по времени lease и уникальные токены. SQL-транзакции остаются
короткими и не держатся во время задержки обработки, публикации в RabbitMQ или HTTP
запроса к webhook.

Результат платежа фиксируется до отправки webhook. Если уведомление не доставлено,
симуляция обработки повторно не запускается: consumer продолжает с уже сохранённым
терминальным статусом. Повторяется именно доставка webhook. Для неё используются две
quorum TTL-очереди с задержками 1 и 2 секунды. После третьей неудачной доставки исходное
сообщение попадает в `payments.dlq`. При передаче в retry-очередь consumer сначала ждёт
publisher confirm и только потом подтверждает текущее сообщение. Если публикация не
подтверждена, текущее сообщение возвращается в очередь.

Exactly-once доставка webhook не заявляется. Получатель может принять HTTP-запрос, после
чего consumer упадёт до записи `webhook_delivered_at`. Повторный webhook в таком случае
корректен для выбранной модели доставки, а стабильный `payment_id` служит ключом
дедупликации на стороне получателя.

Деньги хранятся как `NUMERIC(18, 2)` и передаются через `Decimal`. Все временные метки
используют timezone-aware UTC. Секреты и параметры окружения находятся в typed settings,
локальный `.env` не попадает в Git.

## Запуск

```bash
cp .env.example .env
docker compose up --build -d --wait
```

API доступен на `http://localhost:8000`, RabbitMQ Management находится на
`http://localhost:15673`.

## Проверка

Скрипт создаёт отдельный Compose-проект с тестовыми PostgreSQL и RabbitMQ, применяет
миграции, запускает все проверки и удаляет контейнеры вместе с временными данными при
любом завершении. Основной стек при этом не затрагивается:

```bash
./scripts/test.sh
```

Перед pytest скрипт отдельно проверяет форматирование, Ruff и mypy. Unit-тесты не требуют
Docker. Интеграционная часть работает с настоящими PostgreSQL и RabbitMQ и проверяет
идемпотентность, конкурентные гонки, атомарность outbox, параллельных publisher,
восстановление просроченных claim, ручной ack consumer, повторную доставку, webhook
timeout, точное число попыток и маршрутизацию в DLQ. Pipeline-тест проходит путь от API
через outbox и брокер до сохранённого результата и webhook.
